# 完整备份协议 v1

实际实现采用逻辑数据快照，替代早期文档提出的复制 SQLite 文件方案。这样避免 WAL 遗漏及跨文件切换：恢复通过同一 SQLite 事务替换全部逻辑表，数据库连接和 Schema 不切换。

## 文件组成

ZIP 包含 `manifest.json`、`data.json` 和 `media/<UUID>.jpg|png|jpeg`。清单记录格式版本 1、Schema 版本 1、UTC 创建时间、应用标识，以及每个文件的字节数与 SHA-256。JSON 包含全部账户、收支分类、流水、预算、物品、购买关联及偏好；金额保持最小单位整数，业务日期保留本地日期文本，审计时间保留 UTC 毫秒。

该文件不加密，摘要仅检测损坏，不验证来源。CSV 仅供分析，不能用于完整恢复。

## 导出

在数据库读事务中读取一致的全部表及其不可变图片引用。媒体先发布到私有目录再提交引用，已引用文件不会被原地覆盖。JSON、原图清单属于同一快照，压缩和摘要在独立 isolate 执行。拒绝缺失的原图。

## 恢复

1. 系统选择器读取文件，流式检查压缩文件不超过 50 MB；用户另行确认替换全部数据。
2. 预检 ZIP 中央目录，拒绝重复路径、目录、符号链接、绝对路径、穿越及未知文件；限制最多 1002 个文件、展开总量 100 MB、清单 1 MB。实际解压长度及摘要必须匹配。当前协议仅接受版本 1，未来版本拒绝。
3. 解码逻辑快照，在隔离 SQLite 数据库重建并检查外键与全部仓库业务规则，包括金额、币种、类别、借贷还款、日期与物品购买关联；任何错误不影响当前数据库。
4. 将照片以新 UUID 写入私有目录并 flush，不覆盖现有文件。
5. 在生产数据库单一事务内删除旧逻辑行、插入全部已验证行，重新映射照片。失败回滚全部行并清理本次发布的文件。
6. Riverpod 的数据库流自动刷新。旧照片延迟清理，不要求在提交时完成文件删除。

## 中断与清理

照片发布后、数据库提交前的中断只产生无引用文件；SQLite 事务原子提交确保不会出现部分数据集。提交后的所有图片已经存在。测试注入提交前错误，验证数据库回滚和新照片清理。尚无 Android 进程强杀 / 断电、低内存、大包真机压力测试。

媒体清理只处理私有 `media/` 下名称符合规则、无任何物品引用、修改时间超过一天的文件；一天宽限保护尚未保存的编辑表单。清理在媒体服务首次打开时运行，删除失败下次重试。

## Schema 演进

数据库当前为 v1，快照位于 `lib/data/database/migrations/drift_schema_v1.json`。后续发布 Schema v2 前必须增加数据库迁移、历史数据库测试及备份升级转换；当前不宣称支持不存在的历史版本，也不删除数据库来升级。
